# Scripted OpenAI Recommendation Pipeline — Results Report

**This run used a real OpenAI API key and made real, billed API calls.** All 10 recommendations
in this report were generated by the model itself via `client.responses.parse()` — none were
written or edited by Claude Code's own reasoning. Two authentication attempts were made in this
session; the first key was rejected by OpenAI (`401 Incorrect API key provided`, 0 calls billed,
reported and the user asked to re-check it), the second succeeded.

## 2. THE KEY FINDING: the API is markedly more conservative than the manual-reasoning prototype

The previous (manual-reasoning) prototype produced 19 recommendations across 8 of 10
respondents, with 2 correctly returning no recommendation. This scripted `gpt-4o-mini` run
produced only **4 recommendations across 2 of 10 respondents**, with **8** returning
`NO_DEFENSIBLE_RECOMMENDATION`. This is not primarily a retrieval problem — in most of the 8
decline cases, I verified against `_v2_respondent_bundle.json` that the courses the manual
prototype had recommended (or an equally strong match) **were, in fact, retrieved and present
in the API's own context**:

| Respondent | Stated interest | Course(s) actually retrieved (and manually recommended before) | API's stated reason for declining |
|---|---|---|---|
| `acaf63b5` (D) | Commerce/business/management | `COURSE-049` Business Managemant — **retrieved at rank 1** | Claimed retrieved courses were "primarily language skills and technical training" — an inaccurate description of its own context |
| `00e2c251` (G) | Construction and building | `COURSE-019` Quantity Surveying Assistant (rank 1), `COURSE-023` Construction Site Supervisor (rank 5) — both retrieved | Claimed retrieved courses were "focused on business management, accounting, or other fields" — again inaccurate; also added an unsupported eligibility inference (see §4) |
| `55bdfdcc` (G) | Hotels/restaurants/hospitality, start own business | `COURSE-007` Professional Cookery, `COURSE-011` Baker, `COURSE-050` Cake & Cake Structure, `COURSE-049` Business Managemant — all retrieved | Judged cookery/baking content insufficient for "specific entrepreneurial goals," without combining it with the also-retrieved business course |
| `33aaf2f7` (F) | Wholesale/retail/repair, overqualified in current job | `COURSE-008` Computer Hardware Technician, `COURSE-029` Mobile Phone Repair Technician — both retrieved | Declined; partly cited the respondent's `income_hours_preference` ("fewer hours and less income") as incompatible with full-time courses |
| `0c6c34a2` (F) | Manufacturing/production | `COURSE-012` Refrigeration & AC Technician — retrieved at rank 1 | Declined because the course didn't specifically match "work for a multinational company" |
| `346623df` (F) | ICT, obstacle "skills don't match" | `COURSE-006` ICT Diploma, `COURSE-073` Java Programming — both retrieved (same courses recommended for two *other* respondents in this same run) | Declined because "start my own business" (work-type) outweighed the sector/barrier match |

Two respondents (`a04f7d96`, `465701ee`) were the deliberately weak-evidence test cases and
**correctly** returned `NO_DEFENSIBLE_RECOMMENDATION` — that result is working as intended and
is not part of this concern.

This pattern — genuinely relevant, retrieved evidence not being acted on, sometimes paired with
an inaccurate description of what was actually retrieved — is the central finding of this run
and the main reason for the readiness verdict in §8.

**Likely contributing factors** (not confirmed, offered as hypotheses for the next iteration):
- The governance instructions list 20 prohibited behaviours very prominently, and the model may
  be resolving ambiguity by declining rather than risking a prohibited claim.
- `gpt-4o-mini` is a small, low-cost model; this holistic multi-document judgement task may
  exceed what it reliably reasons well over at ~19-31K input tokens per call (multiple full
  course documents + multiple full profile documents).
- Long context with many retrieved course documents (up to 15 full parents) may dilute attention
  on documents further down the list, though the misses above include rank-1 retrievals too, so
  position alone doesn't explain it.

## 3. What worked well

The 2 respondents that *did* get recommendations (`3a86d117`, `131a2b60`, both with strong,
unambiguous ICT sector preferences) show the pipeline working as designed:
- Both correctly received `COURSE-006` (National Diploma in ICT) and `COURSE-073` (Java
  Programming) — a genuine **within-sector distinction** (broad diploma vs. a specific
  programming skill), not a sector-only match.
- Both recommendations cite `direct_respondent_evidence_used` that is genuinely present in the
  respondent's evidence record (grounding audit: PASS, no mechanical issues).
- `131a2b60`'s recommendation connects the courses to their stated barrier ("No suitable training
  available nearby") and training-type preference ("Professional/technical certification") — a
  real multi-fact synthesis a sector filter alone could not produce.

## 4. A governance-instruction gap the mechanical audit did not catch

`grounding_audit_v2.py` only audits items inside `recommendations[]` — it does **not** scan the
text of `no_defensible_recommendation_reason`. Manual review of that field (§2) found one
instance (`00e2c251`) where the model asserted an unsupported eligibility judgement inside a
decline reason: *"the respondent's educational background (O/L level) may not meet the entry
requirements for many of the courses, which are not explicitly stated but can be inferred."*
This directly contradicts governance rule 5 (no eligibility claim without an explicit stated
requirement) — the model itself says the requirement is "not explicitly stated," yet still
infers a failing grade against it. Because this occurred inside a *decline* rather than a
*recommendation*, it produced no visible harm this run, but the same failure mode inside an
actual recommendation would not have been caught by the current mechanical audit. **This is a
concrete fix needed before scaling** (see §8).

## 5. Borderline-variable usage observed in practice

Two of the ten outputs used exactly the kind of respondent variable this project's own
`respondent_variable_human_review_report.md` flagged as risky if used to drive a feasibility
conclusion on its own:
- `33aaf2f7`: cited `income_hours_preference` (a preference about *current job* hours, flagged as
  a topic mismatch for *course*-schedule decisions) as part of the reasoning for declining.
- `465701ee`: cited `primary_earner_status` ("primary household earner... may limit their ability
  to commit") — hedged with "may," so not a hard rule-4 violation, but leaning on exactly the
  variable this project flagged as not itself implying an attendance constraint.

Neither rises to a grounding-audit FAIL (both are hedged, not stated as fact), but both are
worth watching if the sample is expanded.

## 6-7. Did profile context / full course text help?

- **Profile context**: present in every prompt (labelled `GROUP-LEVEL RESEARCH CONTEXT — DO NOT
  ASSUME...`), but `profile_context_used` was empty in **both** actual recommendations produced
  this run — the model did not draw on profile documents for either successful case, relying
  entirely on Section 1 direct evidence and Section 3 course text. This run does not provide
  positive evidence that profile context added value; it also did not misuse it (no
  profile-to-individual conversion was found).
- **Full course text**: yes, meaningfully — both successful recommendations distinguish courses
  within the same sector on content grounds (general ICT diploma vs. Java-specific programming),
  which the old reduced V2 structured dataset's `skill_area` field alone could not have produced.

## 8. Did the 84-course V2 corpus change anything?

The 5 recovered courses were retrieved for 3 of 10 respondents this run (`COURSE-002` for
`3a86d117` and `131a2b60`; `COURSE-005` for `0c6c34a2`), but **none were actually recommended** —
in every case the model either recommended a different retrieved course or declined entirely.
The larger corpus therefore measurably changed *retrieval* but not, in this sample,
*recommendations*.

## Answers to the six core questions

**A. Does RAG + LLM reasoning provide meaningful value beyond category filtering?**
Sometimes, not consistently, in this run. Where it worked (2/10), it clearly did — genuine
within-sector distinctions grounded in actual course text. But in 3/10 cases (`acaf63b5`,
`00e2c251`, `55bdfdcc`) a naive sector/field-text match would have outperformed this API
configuration, because the model declined to use directly relevant retrieved evidence.

**B. Can the model use respondent circumstances without turning them into unsupported facts?**
Mostly yes, with one caveat. No hard violations of the "cannot attend full-time" type were
found. Two hedged-but-borderline uses of flagged variables were observed (§5), and one clear
unsupported-eligibility inference occurred, but inside a decline reason, not a recommendation
(§4) — still a real governance gap, just not yet observed inside `recommendations[]`.

**C. Does full-text course knowledge improve reasoning vs. the reduced V2 matching dataset?**
Yes, where the model actually engaged with it (both successful recommendations show real
content-level distinction). The bigger problem this run is under-utilization, not
mis-utilization, of that richer text.

**D. Does frozen profile context provide useful additional information?**
Not demonstrated this run — `profile_context_used` was empty in both actual recommendations.
Neither harmful nor clearly helpful; inconclusive with only 2 data points.

**E. Is the system scientifically defensible as an exploratory AI-assisted prototype?**
The auditing and provenance infrastructure is defensible and worked exactly as designed — every
claim in what *was* recommended is traceable and grounded, no protected/technical fields leaked,
no excluded course was ever at risk of being recommended, and the two weak-evidence cases were
handled correctly. What is **not** yet defensible is treating `gpt-4o-mini`'s conservative
declines as a reliable signal that "no course fits" — the evidence above shows several declines
were not well-supported by the model's own retrieved context.

**F. Is it ready to expand to all 362 respondents?**
No, not without changes — see below.

## Fixes required before scaling

1. **Extend the grounding audit to scan `no_defensible_recommendation_reason`**, not just
   `recommendations[]`, for the same prohibited-claim and unsupported-eligibility patterns
   (§4 shows this gap is real, not hypothetical).
2. **Investigate the under-recommendation pattern** before trusting `NO_DEFENSIBLE_RECOMMENDATION`
   at scale: try a stronger model (e.g. a full-size `gpt-4o` or a current reasoning-tier model)
   on the same 10 respondents and compare; and/or rebalance the governance instructions so the
   permission examples are as prominent as the prohibition list, since an instruction set that is
   ~80% "do not" may be inadvertently training the model toward the safest possible answer
   (decline) rather than toward calibrated, evidence-based judgement.
3. **Add an explicit "did you consider retrieved course X?" self-check** for the highest-ranked
   1-2 retrieved parents when the model is about to return `NO_DEFENSIBLE_RECOMMENDATION`, so a
   rank-1 sector match can't be silently mischaracterized as unrelated (as happened twice here).
4. Continue monitoring the two borderline-variable usages (§5) if the sample is expanded, though
   neither is a hard failure yet.

---

## NOT READY

Pending the fixes above. The infrastructure (corpus verification, chunking, retrieval, structured
API integration, token/cost tracking, and the grounding audit for actual recommendations) is
sound and reusable as-is. The recommendation *behaviour* of this specific
model+prompt configuration under-recommends relative to its own retrieved evidence often enough
(demonstrated in 3-6 of 10 cases above) that running it unmodified across all 362 respondents
would likely produce a large number of `NO_DEFENSIBLE_RECOMMENDATION` results that are not
actually justified by the retrieved evidence — not a safe basis for a controlled full-scale run
yet.
